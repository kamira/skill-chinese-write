## 審議席抓到而我沒抓到的

### 抽取順序是判準的一部分(fable)

我送設計時列了 `fiction-long.md` 的三條引用,**漏掉了一個會直接翻案的事實**:
第 49 行是

```
[`references/dialogue.md`](../skills/fiction/references/dialogue.md)
```

**連結文字本身是一個路徑狀的 code span。** 抽取器若先掃反引號,
`references/dialogue.md` 會被當程式碼載體 token、以根為基準、解析不到,
**在一份完全正確的檔案上假紅**。

審議席稱它是 R4 的孿生:「不是規則恆真,是**規則對正確輸入恆假**。」
我先前只想過「規則不火」,沒想過「規則對正確輸入恆火」是同一個病的另一面。

### 基準判別性:綠案必須在錯誤基準下死掉(fable)

防「恆真/恆假」的唯一可機器化手段:

> **每個綠案夾具的每條引用,必須在錯誤基準下解析失敗。**
> 一個在兩種基準下都解析得到的綠案什麼都證明不了。

這條已寫進驗收條件 1,並由證據 B 的第二列證明有效
——「連結改用根基準」這個突變確實打死了 G1 與 G3。

### 封閉文法 vs 列舉(fable)

我問「抽太寬會誤報淹沒真訊號,抽太窄會漏,這個張力怎麼解」。
它把假兩難拆掉:**範圍不是列實例,是列載體文法,而載體文法是封閉的**
——markdown 連結、圍籬、行內 code span,就這三種。過濾用判定式不用名單。

並且釘死:**不設 ignore 名單**,豁免用不可抽取形在文本裡表達。

### 兩類引用的基準要分開寫(codex)

「硬併成同一規則會掩蓋錯誤。」

### 圍籬內路徑不一律算(codex)

「只驗明示為可執行、可複製執行的命令;示意或反例路徑必須可不存在,
**應以語意標記區分,而不是用圍籬位置推定**。」

fable 補完了怎麼做:豁免用語法表達(角括號佔位、含 CJK 段),
**在文本裡看得見**,審稿的人一眼知道那是刻意的假。

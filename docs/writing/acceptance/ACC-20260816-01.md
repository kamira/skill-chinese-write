### 證據 A — 治謊層的四端與突變

```
$ python scripts/version_impact_check.py --self-test
✅ self-test:38 案全過(34 個 case + 4 支獨立測試:理由聚合、分岔歷史、退役復活、基準空轉)

$ python plugins/catalog_check.py --self-test        → rc=0
✅ self-test:…總版號遞增兩案…,且基準空轉兩案(基準即 HEAD 必說「未驗到」、真有分岔不得誤說)。
```

**措辭端是本案的承重斷言。** 原病的形狀不是判錯——`check` 那時是對的,diff 真的是空的
——而是**輸出與真通過一字不差**。所以斷言打在措辭上:空轉訊息不得含 `✅`、
「沒有漏掉」、「都有對應的版號」,且必須含「未驗到」。

突變(只讓治謊層的 `print` 消失,`return []` 保留):

```
突變後 rc = 1
   紅在: ❌ 基準即 HEAD 時沒說「未驗到」——靜默綠與真通過分不出來,
          而 `ref..HEAD` 恆空代表本閘在那個觸發上根本沒判定力
```

**只殺該殺的那一案**,沒有旁案陪葬(`CHG-20260814-08` 記過「突變構造錯了會證明不了
要證的東西,而它看起來很像成功了」)。

### 證據 D — `CI_SINCE_REF` 的三條路徑

```
未設          → SINCE_REF=origin/main(本機與 PR 情境)
零 SHA        → ❌ 硬紅「基準不存在,diff 式的閘無法驗,不得以此為通過」
解析不到      → ❌ 硬紅「基準取不到等於整套版號規則消失」
```

硬紅沿 `[10f]` 的 fail-closed 前例。**這不是 KN-002**:它稀有(只在分支初建或
歷史改寫時發生),而且正是該有人看的時刻。

### 證據 E — 端點驗證(真基準 vs 空轉基準的對照)

`ACC-20260814-10` 命令的那次端點驗證跑在 `be9f55e` 上,而那正是空轉情境
——**它的 diff 閘部分是空綠,不入帳**。依審議席的順序約束,治謊層落地後重跑:

```
$ CI_SINCE_REF=e674a38 bash .github/ci_local.sh     → rc=0
涵蓋 e674a38..HEAD:
    7f8c867 CHG-20260816-01
    be9f55e CHG-20260814-10（#20）
✅ 版號影響閘(基準 e674a387fcd2c7ff8f31a0550e325a726abd51f3):
   skill 內容變更沒有漏掉宿主 bump,…且沒有無驅動源的版號移動
✅ 治理閘通過(唯一真相源:.github/ci_local.sh)
```

`e674a38` 就是 merge #20 那次 push 的 `github.event.before`,所以這是**那次 CI
本來就該有的判定**。

對照組——同一套閘、同樣的空轉情境,現在說什麼:

```
$ CI_SINCE_REF=$(git rev-parse HEAD) bash .github/ci_local.sh   → rc=0
  本閘在這個觸發上**沒有判定力**。這是**未驗到**,不是通過。
  (--since:基準即 HEAD(7f8c867)——`ref..HEAD` 恆空,本閘在這個觸發上**未驗到**…
```

**上一輪那個綠,就是右邊這個情境印出左邊那句話。** 有對照才證明得了修好了什麼。

## 審議席糾正我的三處

1. **plan-check 不是本機缺口**——它在 `verify.sh [2/5]` 有完整迴圈,而 `ci_local [1/18]`
   跑 verify.sh,所以本機一直跑得到。governance 那一步是**第三份重複**。
   真正的缺口是**四支**,不是我報的五支
2. **我漏列了一個受影響的閘**——governance 自己的 version-impact step 同樣在
   main-push 上空轉。我列了它的 catalog 卻沒列它
3. **嚴重度措辭**——「每次 merge 那次 governance 的版號紀律是空的」為真,
   但「所以那些內容沒被驗過」不成立(PR 載體驗過)。空轉是**誠實性**問題,
   未覆蓋(直推 main、stale-base merge)才是覆蓋問題,兩者分開記

## 我在本張裡犯的錯

1. **判斷 `git push` 掛住,連殺四次**——實際是 pre-push hook 在跑整套本機閘,
   日誌會印 `[3/5] 漂移檢查:綠燈可達`。我為此改了憑證路徑、關了互動提示、
   加了 `-s KILL`,**全是在治一個不存在的病**;真正的原因從一開始就在輸出裡,
   只是被 `tail` 與 timeout 截掉了。這是「用推測代替量測」的第五次
2. **等 CI 的迴圈只查 pending 數**——新 run 還沒註冊時 pending=0,迴圈立刻退出
   並回報**上一輪的綠**。我因此一度拿 `ba96a43` 的舊綠當 `fd135a3` 的結果。
   等待條件必須綁 head SHA
3. **`... | tail -6` 後面接 `echo "exit=$?"`**——量到的是 `tail` 的退出碼。
   它印 `exit=0` 的同時螢幕上有 traceback。**同一個病:輸出看起來像通過**,
   而我就是在驗證治謊層的指令裡犯了它
4. **漏 push**——ACC 三讀的 commit 背景指令裡只有 commit 沒有 push
   (前一個指令有,我複製時漏了),是審議席在 merge 前抓到的

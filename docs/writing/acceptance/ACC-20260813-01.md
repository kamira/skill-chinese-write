## 施工中自己抓到、也自己修掉的缺陷

**我引進了一個新 bug 並在驗自己時抓到。** 分母從 `max(total,1000)` 改成真實字數後
`per_k` 可能為 0,四支引擎我加了守衛,但 `style_check.py:415` 的破折號密度漏一處,
空輸入直接 `ZeroDivisionError`。舊版因鉗位而 `per_k` 恆 ≥1,這個洞是這次改出來的。

修法不只補那一行:「我記得加守衛」不是斷言,所以新增 `[10c]`——五支引擎各餵一個空檔,
不准有 traceback。下次有人加 `per_k` 除法忘了守衛,閘會擋,而不是等真實輸入炸掉。

## 審議者的反對意見(採納與否都記下)

### codex 判「格式即規則」豁免是開後門——**採納,已撤掉**

初版對 bizdoc / techdoc 家族整組豁免。codex:「只要把抄來的示範句包裝成公文或規格書,
就能繞過新閘」。理由成立。改成逐對列舉的 `BASELINE`,三個差別:逐對(換檔名就擋)、
會印出來(不靜默)、**只准縮不准長**(清單裡列了卻已無耦合的項目,閘反過來要求刪掉)。

### codex 指 `min_sample_chars = 300` 實質關掉短文本的規則——**部分採納**

它的判詞:「比輸出已知失真的數字誠實,但不能假裝仍完成驗證」;風險是門檻**悄悄擴大成
規則逃生門**。已採納它的具體建議之一:新增 `[10d]`,把「哪幾份預期未驗到」釘死
(目前只有 `fiction-flash/sample-good.md`),名單一多一少都轉紅。

**未採納的部分**:它建議改成逐規則、逐體裁的門檻,並為短體裁保留「絕對次數」規則。
這是對的方向但超出本張範圍(要重新設計密度規則的形狀),列為後續。

### codex 指 `--strict` 只用在一份夾具、其餘警告仍無閘——**未採納,記錄在案**

它的判詞正確:「只能證明那個案例可被閘住,不能證明其餘警告具有 CI 約束力」。
它也給了正確的做法——不是全開,而是**每條提醒規則至少要有一個受 `--strict` 約束的
正例與反例**。本張只為成語密度做到這件事;擬聲詞密度、章節字數、軟限詞等仍無正反例對。
列為後續,不假裝已經有閘。

### codex 建議把 per_k 除法收成 helper——**未採納,記錄在案**

它明確反對「讓 per_k 永遠非零」(會重新引入失真),主張收成一個回傳
「未驗到 / 密度值」的 helper,讓呼叫端無法直接除。這比散落守衛可靠。
本張用 `[10c]` 的端到端防線頂著,helper 重構列為後續。

### 主 agent 不同意 codex 的一處

它建議把 prose 夾具結尾改成「有時候也覺得自己很好笑」。那是把具體動作換成自我評論,
反而更像 AI。未採納,prose 夾具的結尾維持原樣(該檔只動了與引擎 self-test 的耦合)。

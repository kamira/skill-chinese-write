## 這一輪最值得記的一件事

**指標會說謊,而且是往綠的方向說。**

原本的絕對動詞清單照 `chinese.md` 收了單字的「應」與「需」。中文沒有詞界,子字串比對之下「**回應**時間」「**需**求」全都算成絕對動詞——`sample-spec-good.md` 的比例會被灌到接近 1.0,而那個 1.0 完全是假的。

危險在於方向:誤判是往**通過**的方向偏。一個只會變綠的指標比沒有指標更糟,因為它讓人以為有東西在把關。改成只收無歧義的多字動詞(必須/應該/應當/務必/不可/不得/禁止),寧可漏抓「應」的合法用法。

這與 KN-002 是同一個家族但方向相反:KN-002 講的是誤報(往紅偏)會讓人關掉規則;這裡是誤放(往綠偏)會讓人以為被保護。兩者都要求先問「這條規則實際上在量什麼」。

## 代使用者做的決定(請覆核)

1. **規格書與架構說明做成一支 `techdoc`,不是兩支。** 使用者定調「different write should be different skill」,而這兩者的硬規則完全相同,只差結構。判準已寫成 KN-003:硬規則相反才拆,只差結構的用旗標。**這是對使用者那句話的收斂,不是照字面執行**,故列此請覆核。
2. **架構說明「缺圖」升級為硬性違規。** 原文只把圖文互補列為核心手法,未言明強制。
3. **成語改用約 28 條的「文學性成語」小表**,不沿用 fiction 那份 140 條全表。

## 誠實的邊界

1. **驗收者與實作者是同一個。** 中風險原則上要 verifier ≠ implementer,本輪沒有第二個驗收者。
2. **新守衛的紅燈探針只證明了一半。** 把 `spec-good` 當成 bad 餵給守衛,`--kind spec` 那一路守衛確實開火;`--kind arch` 那一路沒開火,因為 `spec-good` 在 arch 下本來就會紅(缺圖)。所以「bad 在兩種 kind 都要被擋」這條的紅燈可達,只在 spec 那一路被直接證明。
3. **模糊形容詞詞表約 20 條,遠非完整。** 「合乎預期」「視情況」這類沒有形容詞但同樣模糊的說法抓不到,SKILL.md 已明標靠人。
4. **「量化描述夠不夠」判不了。** lint 抓得到「快速」,抓不到「回應時間必須合乎預期」。
5. **三支 skill 之後規則檔開始出現重複**(禁用詞結構、`--allow` 行為)。本輪刻意不抽共用層——還看不出哪些真的共通,已記進 KN-003 的觀察區,第二次真正需要時再處理。

## 結論

**通過。** 17 條查核全數通過。`--kind` 的雙向交叉證明它真的改變結論;既有兩支 skill 的 diff 為空;三個閘的載體都納入雙向夾具。三項代決定與五項邊界如實列出,其中第 1 項(把使用者「不同文體不同 skill」收斂為「硬規則互斥才拆」)最需要覆核。

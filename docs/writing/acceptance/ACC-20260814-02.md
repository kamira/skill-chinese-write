## 這一輪最值得記的一件事

**改動前的 CI 也是全綠的。**

兩個目錄被 git 追蹤、與單一真相分岔(對當時的基底 46331e8 實測 11 檔)、其中一份夾具用的是 zh-style 判為硬性違規的半形標點——而 13 道閘一道都沒響。原因不是任何一道閘壞掉,是它們**全部朝同一個方向走**:

| 閘 | 方向 |
|----|------|
| `catalog_check --check` | marketplace 名冊 → 磁碟 |
| `build_suite --check` | `PLUGINS` → plugin 內複本 |
| `skill_inventory_check` 第 2 項 | `PLUGINS` → `skills/` |

三道閘,三個起點,全部是**從名冊出發**。所以「沒被登記在名冊上」這件事本身,對它們是不可見的——不是判定錯,是根本走不到。

這與 CHG-20260810-07 的「規則管三處、斷言只查兩處」是同族,但更難察覺:那次至少有一份名冊列著第三處,對照就看得出來;這次**沒有任何一份文件說過 `plugins/` 底下應該有幾個目錄**,所以連可以對照的東西都不存在。

寫進 KN-001 的第五問是:凡是「A 的每一項都要在 B 裡」的斷言,都要回頭問一次「**B 裡有沒有 A 沒登記的**」。

### 而我補的那道反向閘,自己也是窄的

這一節的下半段是審議席寫的,不是我。

第 6 項補上「磁碟 → 名冊」之後,我在 CHG 寫下的使用者故事是:「我要 `plugins/` 底下**不存在任何**沒被名冊登記的目錄,以便『被 git 追蹤』等於『被治理閘掃得到』。」而實作只查 `plugins/` 的**第一層目錄名**。fable 用兩個實驗證明後半句是假的——`plugins/official/rogue-dir/` 與 `plugins/official/skills/rogue/` 都能被 git 追蹤、都不被 build_suite 同步、而兩道閘都 exit 0。

我當時的處置是把它記進「誠實的邊界」。codex 判不通過,理由一句話:**本張正修 KN-001 第九次,範圍錯位不是可文件化放行的相鄰小洞。**fable 讀完之後改判同意,並補上自己的方案為什麼站不住:把故事的前半句收窄成「第一層」,不能讓後半句變真;要嘛刪掉那個目的子句(等於刪掉本張的立意),要嘛讓斷言追上它。

**所以這一輪 KN-001 觸發了兩次:一次是它管的對象(那兩個孤兒目錄),一次是我修它時寫的斷言自己。**第二次不是我找到的。

一張專門在修「斷言範圍窄於規則範圍」的變更,自己交出一個範圍窄於使用者故事的斷言——而且我還打算用「誠實地記下來」把它放行。這是 KN-001 第一條就禁掉的第三種:**寫成規則的樣子、放在規則文件裡、但沒有人會執行**;只是這次多了一層偽裝,叫做「已知限制」。誠實標示的豁免權,只給**本來就判不了**的東西(KN-003 那些沒有 lint 的 skill),不給**判得了但我沒去判**的東西。

## 誠實的邊界

1. **互審是補做的,不是同輪。**本張的施工與初版 ACC 發生在 `main` 為 46331e8 時,那時 DIR-002 還在 `claude/fixture-cross-review` 上,本分支讀不到它。合併後 DIR-002 生效、本張疊在它上面,才由使用者指示補送兩席。**兩席皆出席、四處分歧全數收斂,故記為互審通過**;但「先收尾再送審」這個順序本身不合 DIR-002 第 1 條的本意,記在此。

   另兩件相關的:

   - **merge 與 rebase 是不可逆動作,依 DIR-002 第 2 條主 agent 不得單方執行。**本次由**使用者直接指示**,不是主 agent 的判斷——DIR-002 管的是判定權從主 agent 往審議席移交,不是使用者自己的決定。記為**依使用者指示執行**,不是單方裁決。
   - **孤兒事實本身是使用者指出的**,我做的是查證與執行,不是發現。本輪的實質發現有三個來源:使用者(孤兒目錄)、fable(兩條逃逸路徑 + 過期實測值)、codex(缺口不得文件化放行 + 同名異型)。**主 agent 獨立找到的是零。**

2. **codex 首次連線逾時 4 次,第 5 次才通(DIR-002 第 3 條的上限)。**其中第 3 次是主 agent 誤指 `model: gpt-5-codex` 而該帳號不支援,是我的錯,不算它的。若第 5 次仍不通,本張就會走單方路徑並標示缺席——**差一次**。這個節奏在實務上比條文寫的更緊。
2. **「刪除而非納管」的依據是 repo 自己寫下的判準**(兩份 SKILL.md 的引擎自述、zh-style 作為第三支引擎沒有 plugin 目錄的先例、KN-003 的觸發面判準),不是我另立的標準。若日後決定要把引擎也上架,推翻的是 KN-003,不是本張。
3. **`catalog_check --since` 在 commit 之前驗不到本張。**它比對的是 `origin/main..HEAD` 的 git diff,工作區的未提交變動不在範圍內——所以「刪檔要 bump」這一項,是先主動 bump、再於 commit 後複驗,不是被閘逼出來的。
4. **第 7 項只斷言登記形狀,不比對內容。**已宣告路徑內的內容漂移歸 `build_suite --check`(實測 exit 1),兩閘相接。仍留的縫:一個**形狀完全合法、但每個檔內容都對**的 plugin,第 7 項不會多問——那本來就是 build_suite 的職責範圍。這是兩席合意的分工,不是漏做。
5. **「合進 main」中途,main 被別的 session 移走了。**下 merge 指令前的例行檢查發現 `main` 已不是我合上去的 268d404,而是 `origin/main` 的 **05f028e**——fixture-cross-review 是以 **squash merge(PR #11)** 進去的,268d404 那條線整個不在 mainline 上。若照原計畫 merge,會把已被壓成一顆的 25 個 commit 再塞一次進 main。改以 `git rebase --onto 05f028e 268d404` 只搬本張的 4 個 commit,零衝突(兩者樹完全相同,`git diff 268d404 05f028e` 為空)。**教訓:merge 前要重讀 target 的現況,不能沿用幾十分鐘前的認知**——分散在多個 worktree 的並行 session 會讓 base 在腳下移動。

6. **編號錯開是對的,但只擋掉了撞號,沒擋掉版號衝突。**本張取 -02 以避開 `claude/fixture-cross-review` 的 -01,rebase 時 CHG / ACC 兩檔確實零衝突;但 `marketplace.json` 的 `metadata.version` 仍然撞了(兩支各自從 2.2.0 往上 bump)。**檔名錯開不等於內容錯開**——凡是「單一計數器」型的欄位,平行分支都會撞,靠命名規則躲不掉。這次靠 `--bump` 對 base 重推導解決,而那正是 `catalog_check` docstring 早就寫過的理由:「人挑版號會對著一個會過期的基底」。

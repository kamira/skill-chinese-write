## 這一輪最值得記的一件事

**我的判準少算了一整個維度,而且是最重要的那個。**

KN-003 建檔時算的是工程成本:重複的規則檔會分岔,所以規格薄的先不拆。那個推論在它自己的前提下無懈可擊——問題出在前提只有一半。

使用者指出的是:**skill 的第一個功能是被找到**。有人說「幫我寫一篇武俠」時,他不會知道要先載入 `fiction` 再加 `--genre wuxia`。一支找不到的 skill,規則檔再乾淨也沒有用。

兩件事都對,而且從頭到尾不衝突——它們管的是不同的問題。改寫後的判準把它們分開問,答案有四種組合,而原本的判準只看得到其中兩種。

這件事的形狀值得記:**一條看起來嚴謹的規則,可能只是在一個太小的問題空間裡嚴謹。**檢查方式不是找它的反例,是問「它有沒有討論到某個維度」——KN-003 從頭到尾沒有出現過「使用者怎麼找到這支 skill」這句話,那才是破綻所在。

## 代使用者做的決定(請覆核)

1. **既有四支不改名。** `writing` 實際上就是評論 skill,叫 `commentary` 更清楚,但改名會動到已發布的 marketplace id,收益只有名稱好看。
2. **`techdoc` 與 `bizdoc` 是 skill 但不是 plugin。** 它們沒有單獨安裝的意義,由前門打包帶入。
3. **catalog 版本跳 major(1.40.0 → 2.0.0)。** 4 → 21 個 plugin 不是 minor。
4. **企劃書收為前門但無 lint。** `chinese.md` 只給了「規格化與標準化」一句,不憑空發明。

## 誠實的邊界

1. **驗收者與實作者是同一個。**
2. **前門的內容沒有任何斷言在管。** 清點腳本查的是「齊備與可達」——SKILL.md 裡的流派配比寫錯了(例如武俠寫成 1-3 次/千字)不會有人發現。這是前門/引擎分層的代價,已寫進 KN-003 的觀察區。
3. **19 支新前門沒有夾具。** 它們沒有 lint,所以沒有紅綠兩端可驗;能驗的只有「明標節存在」與「引擎有被打包」,兩者都做了。
4. **`fu`(賦/駢文)的四六句對偶其實可判**,但那份規則會與 `writing` 的對稱句配額完全相反,必須是獨立引擎。本輪未建,已在 SKILL.md 與 `docs/genres.md` 兩處明說。
5. **marketplace 清單從 4 條變 21 條**,變長了。description 寫成該文體的自然說法以利搜尋,但「太多選項」這個問題沒有被解決。

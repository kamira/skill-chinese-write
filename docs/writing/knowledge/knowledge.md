### 規則

寫下一條可判定的要求時(**風格規則與治理規則同等適用**),同一輪必須做到其中一件:

1. 在 `assets/style_rules.json` 加對應欄位,並在 `scripts/style_check.py` 加斷言;或
2. 在該處明講「這條沒辦法機器判定,靠自己讀」——像 SKILL.md 的五維自評那樣,給結構但不假裝是斷言。

**不允許第三種**:寫成規則的樣子、放在規則文件裡、但沒有人會執行。這種規則比沒有更糟,因為它讓文件看起來完整。

**第二條路不是逃生門。**「明講靠人判斷」的豁免權,只給**本來就判不了**的東西——像 KN-003 那些沒有 lint 的 skill,或「有沒有一個別人沒講過的角度」。**判得了、只是我沒去判**的,寫進「已知限制」不算誠實標示,那是第三種的新偽裝(CHG-20260814-02 第二次觸發時被審議席擋下)。分界很簡單:如果補上斷言的工是可估的,那就補,不要記。

### 為什麼是這條而不是「規則都要能機器檢查」

不是每條都能機器化。「有沒有一個別人沒講過的角度」永遠檢查不了。分界不在「能不能檢查」,而在**有沒有誠實標示**——讀者(和模型)要能一眼看出哪些是硬線、哪些要自己判斷。

### 檢查方式

改完 references 之後,把新增的每一條規則列出來,逐條問:它在 JSON 裡有欄位嗎?沒有的話,文件裡有沒有講明它靠人?兩個都沒有就退回去補。

**再往下問一層**:那條斷言有沒有夾具會踩到?有規則、有斷言、沒有任何夾具會讓它響——文件一樣看起來完整,一樣沒有人在把關(ACC-20260810-02 的章節字數就是這樣被抓到的)。

**再往下問一層**:那份夾具本身對嗎?`bizdoc` 的主旨判定寫成 `[::]`(兩個相同的半形冒號),它一直拒絕每一份標點正確的公文——而夾具能過,是因為夾具的標點也是錯的。**錯的夾具會遮住壞掉的規則**,而且遮得很乾淨:CI 全綠。

**再往下問一層**:那條斷言查的範圍,等於規則管的範圍嗎?規則寫「三處同步」而斷言只比對兩處,和沒有斷言一樣會讓分岔活下來(CHG-20260810-07 就是這樣被抓到的)。

**再往下問一層**:那條斷言是**單向**的嗎?從名冊走訪磁碟的閘,永遠看不到**沒被登記在名冊上**的東西。`plugins/bizdoc/` 與 `plugins/techdoc/` 就是這樣在 main 上活著:被 git 追蹤、與單一真相分岔、三道閘一道都走不到、CI 全綠(CHG-20260814-02)。凡是「A 的每一項都要在 B 裡」的斷言,都要回頭問一次「B 裡有沒有 A 沒登記的」。

**治理規則也要問同樣五句話。**CHG 模板裡的每個欄位、每條「必須」,都要問它有沒有對應的閘、閘的範圍夠不夠寬。

## KN-002 — lint 的門檻要按文本類型分流,不能一套標準打全篇

- tier:shallow
- 日期 / 分支:2026-07-29(UTC+0)/ claude/writing-skill-article-review-92efbc
- tags/scope:lint · 誤報
- 觸發證據:
  1. **CHG-20260728-01**:外部來源把「先 A 再 B」「真正⋯的是」列高風險,但在繁中評論裡是自然口語,硬禁會天天誤報 → 改列軟限密度。
  2. **CHG-20260728-02**:明喻偵測初版把「不像」「很像」「讀起來像機器」這類平常比較一併算入(單篇誤報 4 處)→ 收緊 regex。
  3. **CHG-20260729-01**:條列一加進來就連續誤報三次(粗體上限、平板連段 22/23/22、對稱句「逐句標色/黃是機器」);標題「現象」被當成 2 字的句子扭曲節奏統計;引號內的「它像戒菸貼片」被算成明喻。
- 計數:seen 3 / applied 3 / last-applied 2026-07-29
- 狀態:生效

### 規則

新增或調整任何 lint 判定時,先問這條規則**該套用在哪一種文本**,再問門檻是多少。至少要分開四類:

1. **散文** —— 節奏、對稱、刻意句、長句上限的正常適用範圍
2. **條列** —— 本來就短而齊,句長與對稱一律豁免;自有規則(單項字數上限)
3. **標題** —— 不是句子,不進句長統計;自有規則(不能是結構標籤)
4. **引號內** —— use/mention:作者在**討論**那個詞,不是在用它;修辭類判定一律排除

**禁用詞與密度類是例外,它們全文適用**——引號內的例外走 `--allow` 個案放行,不走自動豁免。分流時要記得補這一刀:CHG-20260729-01 把條列與標題退出句子統計後,禁用詞一度跟著漏抓,是分流引入的回歸。

### 為什麼

誤報的代價高於漏報。lint 是給人看的,一旦它開始對正確的寫法報警,使用者學到的是「忽略警告」,那整套規則就作廢了。分流做得對,規則可以越加越細;分流沒做,規則越細越吵。

### 檢查方式

加一條新判定之後,拿三份東西各跑一次:一篇純散文、一篇有條列與小標的議題型、一篇引用大量原文的稿子。任何一份出現不該有的警告,先修分流再談門檻。

## KN-003 — 拆不拆看觸發面,共不共用看硬規則(2026-08-10 改寫)

- tier:shallow
- 日期 / 分支:2026-08-10(UTC+0)/ claude/techdoc-skill,同日於 claude/genre-split **改寫**
- tags/scope:skill 邊界 · 拆分
- 觸發證據:
  1. **CHG-20260810-03**(新增 `fiction`):拆的理由不是「小說跟評論是兩種文體」,而是 `writing` 的三條硬規則對小說**全是反的**。共用一支 lint 會直接誤殺。
  2. **CHG-20260810-04**(新增 `techdoc`):反過來的情況。規格書與架構說明的硬規則**完全相同**,只差結構;拆開會產生兩份 90% 重複的規則檔,而重複的規則檔一定會分岔。
  3. **CHG-20260810-08**(23 支前門):使用者指出前兩版判準**少算了觸發面**——有人說「幫我寫一篇武俠」時,應該打中一支叫武俠的 skill,而不是先知道要載入 `fiction` 再加 `--genre wuxia`。**skill 的第一個功能是被找到**,而原判準只算了工程成本(規則檔會不會分岔),完全沒討論這一層。
- 計數:seen 4 / applied 4 / last-applied 2026-08-10
- 狀態:生效(第二次改寫,加上第三層)

### 規則:兩件事分開問

原判準把兩個不同的問題混成一個,所以會得出「規格薄的先不拆」這種只從成本面看的結論。拆成兩層之後兩邊都成立:

| 問題 | 判準 | 錯了會怎樣 |
|------|------|-----------|
| **要不要獨立成一支 skill?** | **觸發面**:使用者會不會用這個名字來找它 | 找不到,等於沒做 |
| **規則檔與腳本共不共用?** | **硬規則互不互斥**:相反就各自一份,相同就共用 | 共用會誤殺,分家會分岔 |

答案的四種組合:

1. **獨立 + 自己的引擎**——硬規則與現有的都互斥(`writing` / `fiction` / `techdoc` / `bizdoc`)
2. **獨立 + 指回引擎**——會被單獨尋找,但硬規則與某支引擎相同(`fiction-wuxia`、`spec`、`official`)。plugin 打包時**必須把引擎帶上**,否則裝了跑不動
3. **獨立 + 沒有引擎**——會被單獨尋找,但沒有任何可判定的硬規則(`prose`、`poetry`)。SKILL.md **必須明標「本支沒有 lint,規則靠人判斷」**——這是 [[KN-001]] 的第二條路,不是空頭規則
4. **不獨立**——不會有人用這個名字找它。留在 `docs/genres.md`

### 為什麼原本那條錯了

原本的第三條寫「規格薄到落不成斷言的先不拆」。那句話把「沒有 lint」當成「不該存在」——但 KN-001 從一開始就允許第二條路:**明講靠人判斷**。一支誠實標示自己沒有斷言的寫作指引,是合法的 skill;真正被禁的是**假裝有斷言**。

### 檢查方式

先問「使用者會用什麼字來找它」。會的話就建前門,接著才問「它的硬規則和現有引擎相同還是相反」——相同就指過去並在 plugin 打包時帶上引擎,相反就新建引擎,兩者皆非(沒有硬規則)就明標沒有 lint。

`scripts/skill_inventory_check.py` 把後兩件事變成斷言:沒被任何 plugin 打包的 skill 會紅、前門叫人跑引擎卻沒打包引擎會紅、沒有 lint 又缺明標節會紅。

### 觀察中

23 支之後,規則檔仍然只有四份(引擎)。前門與引擎分層是為了避免分岔,但代價是**前門的內容沒有任何斷言在管**——SKILL.md 寫錯了流派配比不會有人發現。第二次出現前門內容與引擎規則檔不一致時,要考慮把配比也移進規則檔。

     `doc_integrity_check` 掃的是 repo 內的 20 份,**根本沒看到那一份**。
     成因:`git rev-parse --show-toplevel` 從死 worktree 目錄解析會**落回主 repo**,
     而寫檔用的是相對路徑,於是**驗證的樹與寫入的樹不是同一棵**。
     發現後移進 repo(21 份)重跑才是真過。
- 計數:seen 1 / applied 1 / last-applied 2026-08-14
- 狀態:生效

### 規則

**回報任何「閘綠」之前,先證明被驗物在被驗的樹裡。**

留證至少要有兩樣:

1. 被驗檔的**絕對路徑**
2. `git rev-parse --show-toplevel` 的輸出

兩者對不起來就不是驗過,是驗了別的東西。ACC 的證據欄依此紀律填寫。

### 為什麼不是 KN-001 的又一個變體

KN-001 至今十次觸發,全部是「**斷言比規則窄 / 單向 / 夾具本身錯**」——
斷言照的**物件**從來沒錯過,錯的是照的**範圍**或**方向**。

這一次不同:**斷言全對、跑得全綠,但照的不是你改的那棵樹。**
這是驗證完整性的新失效軸,與規則本身的窄或方向無關。所以另立條目。

與 KN-001 的分工:
KN-001 問「這條規則有沒有斷言、斷言涵蓋得夠不夠、跑到它的輸入對不對」;
KN-004 問「**你剛才跑的那個斷言,看的是不是你剛才改的那個檔**」。

### 適用範圍

不限 worktree。任何「產出位置」與「驗證位置」可能分離的情況都適用——
暫存目錄、多 repo、容器內外掛載、以及本 repo 的 `plugins/` 建置產物
(單一真相在頂層、生成物在 plugin 內,驗錯一邊就是同一個病)。

## DIR-001 — 低/中風險變更預先授權:直接 commit、開 PR、merge

- tier:directive(使用者明示指令)
- 日期 / 分支:2026-08-10(UTC+0)/ claude/ai-sdlc-autopilot-handshake-4a3f7a
- tags/scope:global · 治理 · 授權(**全分支適用**)
- 來源原話:「auto commit and create pr and merge, no ask if low or medium risk」
- 狀態:生效

### 規則(邊界寫窄)

**在 `kamira/skill-chinese-write` 這個 repo 內**(2026-08-10 前名為 `kamira/skill-write`),變更風險評為**低或中**時,以下四個閘不再逐次徵詢,直接執行:

1. commit(訊息帶 CHG 編號)
2. push 並開 PR
3. 等 CI 完成
4. CI 全綠後 merge

CI 未完成、非綠、或**判定不出狀態**時,一律停——merge 是單向門,這道閘 fail-closed,不在授權範圍內。

### 不在授權內(仍要停下來問)

- **高風險**變更:資料模型/遷移、認證授權、金流、刪除或不可逆、跨模組介面、安全邊界。命中清單即為高風險,不接受自評降級。
- **永久停點**:不可逆刪除、付款、正式環境資料遷移、安全邊界變更。任何設定都關不掉。
- 風險等級**判定不出來**的時候。分不清就當高風險。

### 為什麼記在這裡而不是只記在 CHG 裡

預先授權是跨變更、跨 session 生效的,寫進單張 CHG 的話下一個 session 讀不到——而讀不到的授權等於沒有授權,下一棒還是會逐次問。

### 撤銷條件

依 CHG-lite 的誤射規則:本授權涵蓋的某一類變更事後被抓到弄壞東西(迴歸或驗收失敗),**本條自動失效**,退回逐次徵詢,直到使用者重新授權。

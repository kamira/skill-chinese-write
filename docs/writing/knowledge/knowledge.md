## KN-001 — 風格規則要嘛有斷言,要嘛明講靠人判斷,不能有空頭規則

- tier:shallow
- 日期 / 分支:2026-07-28(UTC+0)/ claude/writing-skill-article-review-92efbc
- tags/scope:style · lint
- 觸發證據:
  1. **CHG-20260727-01**(v1.0.0 建檔):援引 `docs/ai-sdlc/knowledge` KN-001「治理規則必須有模板欄位 + lint 檢查對應」,把可判定的風格要求全部落成 `style_rules.json` 欄位與腳本斷言。
  2. **CHG-20260728-01**(v1.1.0):對照三支外部工具時發現,v1.0.0 的 `voice.md` 寫了「段落長度也要參差」,但 `style_check.py` 只檢查句長,**沒有任何段落層級的檢查**——同一份文件裡,句長那條有斷言、段落那條沒有,而我在同一輪還引用 KN-001 批評別人的空頭規則。自己犯規。
  3. **CHG-20260728-02**(v1.2.0):`voice.md` 對「字數對稱」有斷言,對同一類的**明喻**與**段末斷語**沒有——外部偵測器逐句判定指出被判最像 AI 的正是後兩者。同一型樣第三度出現,且又是自家犯規。
  4. **CHG-20260729-01**(v1.3.0):使用者五則規格全數落成斷言或明文標示靠人,無空頭規則——本條已內化為改版時的預設動作。
- 計數:seen 4 / applied 4 / last-applied 2026-07-29
- 狀態:生效(四度觸發,前三次皆為自家犯規;改稿與新增規則時一律套用)

### 規則

在 references 裡寫下一條可判定的風格要求時,同一輪必須做到其中一件:

1. 在 `assets/style_rules.json` 加對應欄位,並在 `scripts/style_check.py` 加斷言;或
2. 在該處明講「這條沒辦法機器判定,靠自己讀」——像 SKILL.md 的五維自評那樣,給結構但不假裝是斷言。

**不允許第三種**:寫成規則的樣子、放在規則文件裡、但沒有人會執行。這種規則比沒有更糟,因為它讓文件看起來完整。

### 為什麼是這條而不是「規則都要能機器檢查」

不是每條都能機器化。「有沒有一個別人沒講過的角度」永遠檢查不了。分界不在「能不能檢查」,而在**有沒有誠實標示**——讀者(和模型)要能一眼看出哪些是硬線、哪些要自己判斷。

### 檢查方式

改完 references 之後,把新增的每一條規則列出來,逐條問:它在 JSON 裡有欄位嗎?沒有的話,文件裡有沒有講明它靠人?兩個都沒有就退回去補。

## KN-002 — lint 的門檻要按文本類型分流,不能一套標準打全篇

- tier:shallow
- 日期 / 分支:2026-07-29(UTC+0)/ claude/writing-skill-article-review-92efbc
- tags/scope:lint · 誤報
- 觸發證據:
  1. **CHG-20260728-01**:外部來源把「先 A 再 B」「真正⋯的是」列高風險,但在繁中評論裡是自然口語,硬禁會天天誤報 → 改列軟限密度。
  2. **CHG-20260728-02**:明喻偵測初版把「不像」「很像」「讀起來像機器」這類平常比較一併算入(單篇誤報 4 處)→ 收緊 regex。
  3. **CHG-20260729-01**:條列一加進來就連續誤報三次(粗體上限、平板連段 22/23/22、對稱句「逐句標色/黃是機器」);標題「現象」被當成 2 字的句子扭曲節奏統計;引號內的「它像戒菸貼片」被算成明喻。
- 計數:seen 3 / applied 3 / last-applied 2026-07-29
- 狀態:生效

### 規則

新增或調整任何 lint 判定時,先問這條規則**該套用在哪一種文本**,再問門檻是多少。至少要分開四類:

1. **散文** —— 節奏、對稱、刻意句、長句上限的正常適用範圍
2. **條列** —— 本來就短而齊,句長與對稱一律豁免;自有規則(單項字數上限)
3. **標題** —— 不是句子,不進句長統計;自有規則(不能是結構標籤)
4. **引號內** —— use/mention:作者在**討論**那個詞,不是在用它;修辭類判定一律排除

**禁用詞與密度類是例外,它們全文適用**——引號內的例外走 `--allow` 個案放行,不走自動豁免。分流時要記得補這一刀:CHG-20260729-01 把條列與標題退出句子統計後,禁用詞一度跟著漏抓,是分流引入的回歸。

### 為什麼

誤報的代價高於漏報。lint 是給人看的,一旦它開始對正確的寫法報警,使用者學到的是「忽略警告」,那整套規則就作廢了。分流做得對,規則可以越加越細;分流沒做,規則越細越吵。

### 檢查方式

加一條新判定之後,拿三份東西各跑一次:一篇純散文、一篇有條列與小標的議題型、一篇引用大量原文的稿子。任何一份出現不該有的警告,先修分流再談門檻。

## KN-003 — 拆 skill 的判準是硬規則互斥,不是文體名字不同

- tier:shallow
- 日期 / 分支:2026-08-10(UTC+0)/ claude/techdoc-skill
- tags/scope:skill 邊界 · 拆分
- 觸發證據:
  1. **CHG-20260810-03**(新增 `fiction`):拆的理由不是「小說跟評論是兩種文體」,而是 `writing` 的三條硬規則對小說**全是反的**——必須有第一人稱(小說主流是第三人稱限知)、結尾禁短句(斷頭台法則要的就是戛然而止)、刻意句上限 3 處(武打段落要的就是密集對偶)。共用一支 lint 會直接誤殺。
  2. **CHG-20260810-04**(新增 `techdoc`):同樣的問題反過來出現。使用者定調「different write should be different skill」,照字面推是規格書一支、架構說明一支;但兩者的硬規則**完全相同**(修辭趨近 0、禁模糊形容詞、禁誇張),只差結構。拆開會產生兩份 90% 重複的規則檔,而重複的規則檔一定會分岔。
- 計數:seen 2 / applied 2 / last-applied 2026-08-10
- 狀態:生效

### 規則

要決定兩個文體是同一支 skill 還是兩支,依序問:

1. **硬規則互斥嗎?**(同一條規則,一邊要、另一邊禁)→ **拆成兩支**。共用必然誤殺,而誤殺會讓使用者關掉整套規則。
2. **只差結構嗎?**(硬規則相同,差在編號 vs 圖、出版 vs 網文)→ **一支 + 旗標**(`--kind` / `--mode`)。兩份規則檔會分岔。
3. **規格薄到落不成任何斷言嗎?** → **先不拆**,留在 `docs/genres.md` 的對照表。用四五行的規格生一個 skill,產出的是空頭規則(見 [[KN-001]])。

### 為什麼不是「一種文體一支」

那句話的字面推到底是 20 個文體 20 支 skill,而其中 11 支的核心指標是修辭比例——沒有程式量得出「幾成是譬喻」,那 11 支會全部沒有斷言。**skill 的邊界應該畫在規則會不會打架,不是畫在名詞不同。**

### 檢查方式

拆之前把兩邊的硬規則列成一張對照表,逐條問「這一條在另一邊是要、是禁、還是無所謂」。出現一個「一邊要、一邊禁」就拆;整張表都是「相同」或「無所謂」,就是同一支的兩個旗標。

### 觀察中

三支 skill 之後,規則檔的共通部分(如禁用詞的資料結構、`--allow` 的行為)開始出現重複。本輪**不預先抽共用層**——還看不出哪些真的共通。第二次真正需要跨 skill 共用時再處理。

## DIR-001 — 低/中風險變更預先授權:直接 commit、開 PR、merge

- tier:directive(使用者明示指令)
- 日期 / 分支:2026-08-10(UTC+0)/ claude/ai-sdlc-autopilot-handshake-4a3f7a
- tags/scope:global · 治理 · 授權(**全分支適用**)
- 來源原話:「auto commit and create pr and merge, no ask if low or medium risk」
- 狀態:生效

### 規則(邊界寫窄)

**在 `kamira/skill-chinese-write` 這個 repo 內**(2026-08-10 前名為 `kamira/skill-write`),變更風險評為**低或中**時,以下四個閘不再逐次徵詢,直接執行:

1. commit(訊息帶 CHG 編號)
2. push 並開 PR
3. 等 CI 完成
4. CI 全綠後 merge

CI 未完成、非綠、或**判定不出狀態**時,一律停——merge 是單向門,這道閘 fail-closed,不在授權範圍內。

### 不在授權內(仍要停下來問)

- **高風險**變更:資料模型/遷移、認證授權、金流、刪除或不可逆、跨模組介面、安全邊界。命中清單即為高風險,不接受自評降級。
- **永久停點**:不可逆刪除、付款、正式環境資料遷移、安全邊界變更。任何設定都關不掉。
- 風險等級**判定不出來**的時候。分不清就當高風險。

### 為什麼記在這裡而不是只記在 CHG 裡

預先授權是跨變更、跨 session 生效的,寫進單張 CHG 的話下一個 session 讀不到——而讀不到的授權等於沒有授權,下一棒還是會逐次問。

### 撤銷條件

依 CHG-lite 的誤射規則:本授權涵蓋的某一類變更事後被抓到弄壞東西(迴歸或驗收失敗),**本條自動失效**,退回逐次徵詢,直到使用者重新授權。

## 動機

使用者要「skill 只分大類」,目標形狀是**一個 plugin `fiction` → 一支大類 skill →
六支流派各是一個 slash command**(`/fiction:long` 這種)。

這需要 `plugins/<p>/commands/`。**但本 repo 的治理閘現在會擋掉它**——
`scripts/skill_inventory_check.py` 的 `PLUGIN_TOP_ALLOWED` 只允許四個項目,
`commands/` 一放進去第 7 步樹形閘立即紅。

所以搬遷之前必須先讓閘認得新樹形。**本張只做這件事,不動任何 skill 內容、
不動 marketplace、不刪任何 plugin id。**

## S1 停驗點(已通過,證據在此)

不是靠文件推測:**現行運作中的 `ai-sdlc-suite` plugin 本身就有 `commands/`**
(`plugins/ai-sdlc-suite/commands/autopilot-accept.md`),本 session 用過
`/ai-sdlc-suite:ai-sdlc-handshake`。順帶確認三件:

1. frontmatter 只要 `description:` 即可,`name` 非必填(檔名即命令名)
2. 命令檔支援 `$ARGUMENTS`
3. **plugin 頂層不是只能有四個項目**——該 plugin 還有 `ci-templates` / `hooks` / `mcp`

第 3 點改變了白名單的性質:`PLUGIN_TOP_ALLOWED` **從來不是「平台允許什麼」的鏡像,
是「本 repo 治理了什麼」的登記簿**(審議席原話)。擋下 `hooks/` 的理由因此從
「平台不支援」改成「本 repo 未登記」——**理由變了,要不要擋沒變**。

## 驗收條件

### A. 白名單與樹形(第 7 步)

1. **合法**:plugin 內含 `commands/long.md`(只有 `description` frontmatter、內含 `$ARGUMENTS`)→ inventory 通過
2. **防回歸(拼錯)**:未知頂層目錄 `command/`(少了 s)仍被擋
3. **防回歸(平台合法但未登記)**:`hooks/` 仍被擋,且**報錯訊息必須寫「未登記」而非「非法」**,
   並指明放行路徑是「開 CHG 把它登記進 `PLUGIN_TOP_ALLOWED` 並補同步與夾具」。
   未來真要用 hooks 是一次**登記變更**,不是拆閘。

   > 這一條是七項裡最有價值的。拿拼錯當紅端只證明閘擋得住打字錯誤;
   > 拿平台合法、他 repo 實用的目錄當紅端,證明的是閘擋得住
   > 「平台合法但本 repo 未治理」——**那正是孤兒目錄事故的形狀:
   > git 合法、平台合法、沒人管。**

### B. 同步(build_suite)

4. **新增**:來源有 command、生成端沒有 → `--check` 先紅;`build_suite` 後轉綠
5. **漂移**:兩邊同名 command 內容不同 → 必紅
6. **刪除**:生成端有來源端沒有的孤兒 command → 必紅;build 後移除
7. **多檔**:至少兩個夾具 command,證明不是只複製單一固定檔名

### C. 反向(磁碟 → 名冊)——本張的核心,前科的直接對策

> 孤兒事故的教訓寫在 `skill_inventory_check.py` 的 docstring:
> **三道閘全是名冊→磁碟,不在名冊裡的東西誰都走不到。**
> commands 若只做 A、B,又是同一個方向。**前科不是缺閘,是缺方向。**

8. **磁碟→名冊**:頂層 `commands/` 來源樹裡存在、但**沒有任何 plugin 宣告要打包**的
   command 檔 → 必紅。宣告收在**單一登記簿**(`build_suite.py` 的 `PLUGINS` 旁增設對照,
   或擴充其值),並寫成**雙向相等**的純函式——單向包含就是上次出事的寫法。
9. **plugin 內未宣告條目**:`plugins/<p>/commands/` 出現未宣告的檔 → 必紅。
   且**分工要寫進 docstring**:該目錄整個視為建置產物,`build_suite --check` 對它做雙向比對;
   第 7 步只管 `commands` 這個節點的存在與型別。
   **不寫明歸屬,兩閘之間的縫就是下一個孤兒的住處。**

### D. 紅端要永久可達,不是開發當下亮過一次

10. 上述每一條新判定都要進 `--self-test` 的**合成樣本**(比照現行 `SHAPE_CASES` / `TRIO_CASES`),
    CI 每輪重驗。**零失敗與引擎壞掉看起來一樣。**
11. command frontmatter 至少斷言 `description:` 存在且非佔位——
    S1 已確認那是平台唯一必要欄位,缺它的 command 會靜靜裝上然後壞掉

### E. 可判定的完成定義(缺一即未完成)

1. `python3 scripts/skill_inventory_check.py --self-test` → exit 0,
   且輸出的逃逸路徑條數 **> 現行 5 條**(新增合成紅端計入並列名)
2. `python3 scripts/skill_inventory_check.py --repo .` → exit 0
3. 三步演練留證於 ACC(輸出原文 + exit code):
   (a) 頂層 commands 加一檔 → `build_suite --check` exit 1;
   (b) plugin 內塞未宣告檔 → exit 1;
   (c) `build_suite` 同步後 → `--check` exit 0
4. 至少兩個夾具 command 在 `tests/fixtures/`
5. 推上分支後 governance workflow **十七步全綠**(含 `catalog_check --since`、`verify.sh`)
6. `git diff --stat main...HEAD` 觸及範圍只有「範圍」表列的四處

## 停點

**走 DIR-001 自動**:本 CHG 補記、改 inventory 與 build 及其夾具、跑紅燈修正跑完整 CI。

**必停雙席裁決**:

1. S2 全綠後,**進入第一批真實 commands / skill 搬遷之前**
2. 任何測試要求**放寬白名單**、改 `tools/` 隨身副本、或擴張同步範圍
3. **非預期紅**——先紅後綠是工序,本張驗收條件裡已列的預期紅不觸發停點;
   不在預期清單上的任何紅才停
4. 發現現有生成物**不是單向來源**
5. 施工中若發現 commands **無法靠目錄慣例生效**、需要動 `plugin.json` 或
   marketplace 條目結構才能宣告 → 停。S1 的證據是目錄慣例層級的;
   manifest 層級一旦被牽動,施工範圍的前提就變了
6. marketplace **刪除舊 id 前**,以及刪除後驗證失敗時
7. CHG 收尾與提交前

**使用者已明示同意刪除舊 plugin id**,所以刪除點不再需要問使用者;
但它仍是不可逆切換點,**必須先經雙席裁決與完整驗證**。

## 施工事故(如實記,已建 KN-004)

**我把新開的 CHG 寫進一個已失效的 worktree 目錄,然後回報「三道閘全過」——那是假的。**

該目錄(`.claude/worktrees/beautiful-hopper-207726`)只剩 `docs/`,已不在
`git worktree list` 裡。三道閘掃的是 repo 內的 20 份,**根本沒看到那一份**。

成因:`git rev-parse --show-toplevel` 從死 worktree 目錄解析會**落回主 repo**,
而我寫檔用相對路徑,於是**驗證的樹與寫入的樹不是同一棵**。
發現後移進 repo(21 份)重跑才是真過。

已建 **KN-004**:回報任何「閘綠」之前,先證明被驗物在被驗的樹裡,
證據須含被驗檔絕對路徑與 `git rev-parse --show-toplevel` 輸出。
審議席判它是**新的失效軸**而非 KN-001 的變體——
KN-001 的十次全是「斷言比規則窄 / 單向 / 夾具錯」,斷言照的**物件**沒錯過;
這次是**斷言全對、跑得全綠,但照的不是你改的那棵樹**。

## 複審抓到的三個逃逸孔(初版全部無聲通過)

審議席用合成 probe 直接打 `sync_commands`,抓到三處 exit 0 的盲區,全部已修並各配紅端:

1. **頂層 `commands/` 的非 .md 檔**——反向斷言只掃 `suffix == ".md"`,看不見
2. **頂層 `commands/` 的子目錄**——`iterdir + is_file`,看不見
3. **已宣告 plugin 的 `commands/` 子目錄**(`commands/deep/evil.md`)——
   sync 只看第一層檔案、inventory 只驗節點型別不看內部。
   **這一個會被打包出貨**,正是本 CHG 自己寫的「兩閘之間的縫就是下一個孤兒的住處」。

另外兩項未達標也已補:**D-11 先前完全沒實作**(command frontmatter 的 `description`
斷言);**A-3 的報錯訊息**缺「未登記 ≠ 非法」與放行路徑,且「只同步 skills/」的敘述已過時。

## E-4 改判(審議席裁決)

原文要求「兩個夾具 command 放 `tests/fixtures/`,證明同步不是單檔名寫死」——
但兩個條件**互斥**:`build_suite` 走不到 `tests/fixtures/`;而放進
`plugins/<p>/commands/` 就算第一批真實搬遷(codex 原話:「**不因名為夾具而改變**」),
還會被**打包進可安裝的 plugin、對外發布測試檔**。

改判:E-4 由 `build_suite --self-test` 滿足——暫存目錄合成假樹 + 合成名冊,
**直接打 `sync_commands` 正式邏輯**。兩個命令分屬不同 plugin 且檔名不同,
單檔名寫死的實作會在這裡露餡。機制的證明留在機制批,不移下一張。

`COMMANDS` 正式登記簿**維持空白**,零真實 command 進 repo。

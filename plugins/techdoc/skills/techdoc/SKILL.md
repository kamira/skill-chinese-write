# techdoc — 中文技術文件

> 繁體中文。這支管的是**讀的人不必猜**:每個形容詞背後有沒有數字,每個模組關係有沒有圖。

## 為什麼規格書與架構說明是同一支

本 repo 的原則是「不同文體不同 skill」,但判準是**硬規則互不互斥**,不是文體名字不同:

| | `writing` vs `fiction` | 規格書 vs 架構說明 |
|---|---|---|
| 第一人稱 | 一個必須有,一個不需要 | 兩個都不該有 |
| 結尾短句 | 一個禁,一個要 | 兩個都無所謂 |
| 修辭 | 一個限量,一個是文體本身 | **兩個都趨近於零** |
| 模糊形容詞 | 未規範 | **兩個都禁** |
| 差在哪 | 硬規則**相反**→ 必須拆 | 只差**結構**→ 一支兩 kind |

硬規則相反的共用會誤殺;只差結構的拆開會產生兩份必然分岔的規則檔。詳見 knowledge KN-003。

## 兩份規則,分工

| 檔案 | 管什麼 | 什麼時候讀 |
|------|--------|-----------|
| [`references/spec.md`](references/spec.md) | 規格書:模組化編號、絕對動詞、量化描述、驗收標準怎麼寫 | 寫規格時 |
| [`references/architecture.md`](references/architecture.md) | 架構說明:圖怎麼配、由大到小、技術選型的權衡怎麼記 | 寫架構文件時 |

## 三條硬規範(兩種 kind 都適用)

1. **模糊形容詞一律換成具體數據。** 快速、良好、適當、盡量、大幅、顯著⋯⋯這一整類 lint 直接擋。「快速回應」沒有意義,「P95 < 200ms」才有——差別在驗收那天指得出來還是各說各話。
2. **禁止誇張與情緒詞。** 非常、完美、革命性、驚人。技術文件不需要說服,只需要說清楚。
3. **修辭配額。** 規格書 **0 處**;架構說明 **2 處**,且只用於把抽象架構類比成讀者已知的實物(微服務像積木)。超過就是裝飾。

## 各自的結構規範

| | 規格書 `--kind spec` | 架構說明 `--kind arch` |
|---|---|---|
| 硬性 | 修辭 0 處 | **沒有任何圖 → 擋** |
| 警告 | 缺模組化編號(1.1.1);條列含絕對動詞低於 30% | 缺權衡/取捨/決策段落 |

「必須有圖」是硬性,理由與 ai-sdlc 的設計圖規則同源:**讀不了的確認材料換不到確認**。散文描述模組關係最容易被點頭放過,也最容易錯——「你把那個模組接到反邊了」正是散文表達最差、而圖一眼看得出來的東西。

認三種畫法:mermaid 區塊、markdown 圖片、ASCII 方框。用了認不出的畫法加 `--allow-no-diagram`——**那個旗標會被印出來**,放行要留痕。

## 三條靠你自己判斷(lint 判不了,明說)

1. **量化描述夠不夠。** lint 抓得到「快速」,抓不到「回應時間必須合乎預期」這種沒有模糊詞但也沒有數字的句子。
2. **由大到小的邏輯遞進。** 架構說明要從整體結構走到模組,再走到資料流。順序對不對,只有讀的人知道。
3. **圖畫得對不對。** lint 只確認有圖。依賴方向畫反了它看不出來——那正是要給人看的原因。

## 交稿前跑 lint

```
python3 skills/techdoc/scripts/techdoc_check.py 規格.md --kind spec
python3 skills/techdoc/scripts/techdoc_check.py 架構.md --kind arch
```

引用他人原文而不得不出現禁用詞時,用 `--allow` 個案放行:

```
python3 skills/techdoc/scripts/techdoc_check.py 規格.md --kind spec --allow 彈性
```

規則的單一真相在 [`assets/techdoc_rules.json`](assets/techdoc_rules.json)。要加詞或調門檻改那份,不要改腳本。

## lint 之後:自己問五件事

| 維度 | 問題 | 1 分 | 10 分 |
|------|------|------|-------|
| **可驗收** | 每條需求驗收那天指得出過或沒過嗎 | 「體驗要好」 | 「P95 < 200ms,壓測腳本在 x」 |
| **可引用** | 開會時說得出是第幾條嗎 | 一整段散文 | 2.1.3 |
| **邊界** | 有沒有講清楚不做什麼 | 只寫要做的 | 有「本規格不涵蓋」 |
| **為什麼** | 選型有沒有記下為什麼不選另一個 | 只有結論 | 有權衡表與被否決的選項 |
| **失效** | 有沒有寫已知限制 | 全篇都是順利路徑 | 明列瓶頸與觸發條件 |

**低於 35 分就回去改。**

> 五維評分的形式改編自 `stephenturner/skill-deslop`(MIT),維度為本 skill 自訂。規範內容改編自使用者提供的 `chinese.md` 技術與工程應用文體節。

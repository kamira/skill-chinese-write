# spec — 規格書

規格書的唯一目的:**驗收那天指得出過或沒過。**

## 修辭比例是零

不是「很少」,是零。任何譬喻、擬人、誇張都會讓讀的人多一個要猜的東西,而規格書的讀者是要照著做的人,不是要被說服的人。lint 對 `--kind spec` 的修辭配額設 0 處。

## 模糊形容詞:硬性違規

這是技術文件最貴的缺陷。「快速回應」在寫的時候大家都點頭,驗收時才發現各自想的是不同的數字。

| 別寫 | 寫成 |
|------|------|
| 快速回應 | 回應時間 P95 < 200ms |
| 處理大量資料 | 單次上限 100,000 列 |
| 適當的重試 | 最多重試 3 次,間隔 1s / 2s / 4s |
| 良好的錯誤訊息 | 錯誤回應含 `code`、`message`、`request_id` |
| 盡快通知 | 5 分鐘內送出通知 |

詞表在 `assets/techdoc_rules.json` 的 `vague_adjectives`。引用他人原文時用 `--allow` 個案放行。

**lint 抓不到的那一半**:沒有模糊詞、但也沒有數字的句子——「回應時間必須合乎預期」。這條靠你自己讀,SKILL.md 已明標。

## 絕對動詞

需求句要講清楚是必須還是可選:**必須 / 應該 / 應當 / 務必 / 不可 / 不得 / 禁止**。

lint 檢查條列中含絕對動詞的比例,低於 30% 會提醒。門檻是比例而不是逐條硬性,因為不是每個條列都是需求句——也有純說明句,逐條硬性會誤報,而誤報的代價高於漏報。

**刻意不收單字的「應」與「需」**:中文沒有詞界,子字串比對會讓「回應時間」「需求」都算成絕對動詞,把比例灌水成假的通過。一個只會變綠的指標等於沒有指標。

## 模組化編號

`1`、`1.1`、`1.1.1`。用途只有一個:開會時說得出「2.1.3 那條」。

lint 找不到任何 `1.1` 形式的編號時會提醒。這是警告不是硬性——短文件用不到三層編號很正常。

## 驗收標準怎麼寫

每條需求要能對應到一個**看得到結果的動作**:

- 對應哪個自動化測試,跑在哪裡
- 效能門檻用什麼腳本量,結果留在哪個路徑
- 負向情境怎麼觸發(例:注入資料庫錯誤,斷言回應不含 `SQLSTATE`)

「由負責人自行判斷」不是驗收標準,是把問題留到最後一天。

## 邊界

寫清楚**不涵蓋什麼**。一份沒有邊界的規格,任何人都可以在驗收時說「這也應該要有」。

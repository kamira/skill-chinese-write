# architecture — 架構說明

架構說明的價值不在「我們做了什麼」,在**「為什麼不是另一個做法」**。

## 沒有圖就是不合格

lint 對 `--kind arch` 把缺圖列為**硬性違規**。理由與 ai-sdlc 的設計圖規則同源:

散文描述模組關係,最容易被點頭放過,也最容易錯。「你把那個模組接到反邊了」「資料其實是往另一個方向流的」——這正是散文表達最差、而圖一眼看得出來的東西。**讀不了的確認材料換不到確認,只換到默許。**

認三種畫法:

1. ` ```mermaid ` 區塊(GitHub 直接算圖)
2. markdown 圖片 `![...](...)`
3. ASCII 方框(`┌─┐` 或 `+---+`)

用了認不出的畫法加 `--allow-no-diagram`。那個旗標會被印在報表上——**放行要留痕**,不能靜悄悄過。

**lint 只確認有圖,不確認圖對不對。** 依賴方向畫反了它看不出來,那正是要給人看的原因。

## 兩張圖,分工

| 圖 | 回答什麼 |
|----|---------|
| 架構圖 | 有哪些模組,誰依賴誰,箭頭往哪邊 |
| 流程圖 | 一次請求走過哪些元件,順序是什麼 |

只畫一張的話,通常缺的是第二張——結構圖看得出誰連誰,看不出一次呼叫實際跑過哪裡。

## 由大到小

整體結構 → 模組關係 → 資料流 → 已知限制。

先給一句話講完整體(「三個模組,依賴方向只有一個」),再展開。反過來寫的文件,讀者要讀到最後才拼得出全貌。

這條 lint 判不了,靠你自己讀。

## 類比:限量兩處

架構說明是唯一允許修辭的技術文件,但用途很窄:**把抽象架構類比為讀者已知的實物**。微服務像積木、佇列像取號機——這種。

超過兩處就變成裝飾,lint 會擋。規格書則是 0 處。

## 權衡才是重點

lint 會找標題含「權衡 / 取捨 / trade-off / 決策」的段落,找不到就提醒。

一張權衡表至少要有四欄:

| 決策 | 選項 | 前提假設 | 為什麼這樣選 |
|------|------|----------|--------------|

**「前提假設」那一欄最容易被省略,也最重要**——它是這個決策日後會失效的條件。「目前尖峰每分鐘 40 個任務」寫下來之後,有一天到 500 個,所有人都知道要回來重看這一格。

## 已知限制

寫下來的限制是資產,沒寫的限制是地雷。至少寫兩種:

- **現在就不支援的**(例:不支援斷點續傳,工作者中途死亡會從頭跑)
- **成長到某個量會失效的**(例:任務量到每分鐘 500 個以上,佇列的鎖競爭會成為瓶頸)
